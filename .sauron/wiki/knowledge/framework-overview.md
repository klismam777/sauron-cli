# Sauron CLI Framework Overview

## 1. Context
Sauron CLI is a local infrastructure framework for preventing AI context amnesia in software repositories. It injects a structured memory system into a target project through `.sauron/`, `.agents/`, `AGENTS.md`, and assistant-specific configuration files.

The framework does not execute application business logic. Its product surface is governance: it installs rules, wiki folders, integrity metadata, and adapter-specific memory files so AI coding assistants can read durable context and are obligated to write decisions back to the project wiki.

## 2. Responsibility
The framework is responsible for:
- Detecting a repository's stack and active AI tools through lightweight heuristics.
- Generating or updating global agent instructions in `AGENTS.md`.
- Injecting base wiki and memory templates into `.sauron/` and `.agents/`.
- Routing memory payloads to supported AI tools through registered adapters.
- Protecting user-maintained wiki content from accidental overwrites.
- Auditing structural integrity through hashes and expected files.
- Uninstalling Sauron bindings while preserving the wiki by default.

The framework is not responsible for:
- Synchronizing wiki files with a remote service inside the current implementation.
- Deep source-code indexing beyond root-level heuristics and selected known files.
- Enforcing agent behavior at runtime outside the files consumed by each AI tool.
- Running tests for target repositories.

## 3. Architectural Decisions

### Decision 1: CLI Commands as Feature Boundaries
- **Problem**: The tool needs lifecycle commands with different user flows and output modes.
- **Options Considered**:
  - Centralize all command logic in the executable entrypoint.
  - Split commands into feature modules.
- **Choice**: Use `src/features/{init,doctor,uninstall}` as command/service boundaries.
- **Justification**: Each command owns its orchestration while shared infrastructure remains in `src/core`, `src/domain`, and `src/presentation`.
- **Trade-offs**: The command handlers still contain presentation-specific copy and onboarding flow details, so future UI changes may touch feature command files.

### Decision 2: Adapter Registry for AI Tool Isolation
- **Problem**: Each AI assistant expects a different local rule format and file location.
- **Options Considered**:
  - Hardcode all assistant file writes in `InitService`.
  - Use one adapter per AI with a shared contract.
- **Choice**: Register concrete adapters through `AdapterRegistry` and resolve them by configured target IDs.
- **Justification**: This keeps assistant-specific behavior isolated behind `IAgentAdapter.detect`, `inject`, and `clean`.
- **Trade-offs**: Target names must normalize exactly to registered adapter IDs, and unsupported names fail the init flow.

### Decision 3: Manifest Hashes for Managed Files
- **Problem**: Re-running `sauron init` should update generated files without destroying organic user edits.
- **Options Considered**:
  - Always overwrite generated files.
  - Never overwrite existing files.
  - Compare generated-file hashes from the last manifest.
- **Choice**: Store SHA-256 hashes in `.sauron/.manifest.json` and use them to detect conflicts.
- **Justification**: Files unchanged since the last Sauron write can be updated silently; mutated files require conflict resolution.
- **Trade-offs**: Mutable files such as `.sauron/wiki/**` and `.agents/rules/memory.md` are intentionally excluded from manifest governance, so their consistency depends on wiki discipline and doctor summary checks.

### Decision 4: Non-Destructive Wiki Recipes
- **Problem**: Stack-specific knowledge should be bootstrapped without overwriting local project knowledge.
- **Options Considered**:
  - Recopy wiki templates on every init.
  - Copy recipes only when missing and update `summary.json`.
- **Choice**: `WikiBootstrapper` writes recipe files only if absent and always maintains routing metadata.
- **Justification**: The wiki is the project's living source of truth, so local edits must survive upgrades.
- **Trade-offs**: Existing recipe content is not refreshed when templates improve, unless a future migration process is added.

### Decision 5: Canonical Memory Payload for Adapter Injection
- **Problem**: Re-running `sauron init` could read `.agents/rules/memory.md` after it had already been generated by an adapter, causing recursive `SAURON START/END` nesting.
- **Options Considered**:
  - Keep reading the installed `.agents/rules/memory.md` file.
  - Strip wrappers from installed files before reinjection.
  - Treat the template memory file as the canonical payload source and let adapters own generated outputs.
- **Choice**: Load memory rules from `templates/.agents/rules/memory.md`, normalize frontmatter and existing Sauron markers defensively, and skip copying `.agents/rules/memory.md` as a generic template file.
- **Justification**: Adapter outputs and template inputs now have separate responsibilities, making `init` idempotent for passive memory rules.
- **Trade-offs**: If a user manually edits `.agents/rules/memory.md`, `init` will regenerate it from the canonical template for selected Antigravity targets. Durable custom rules should be represented in the wiki or source templates, not in generated adapter output.

## 5. Current State

### Entry Point and Commands
`src/index.ts` creates the Commander program named `sauron` and exposes three commands:
- `sauron init`: installs or updates the memory system.
- `sauron doctor`: audits registry, manifest, wiki summary, and adapter files.
- `sauron uninstall`: removes Sauron bindings and optionally purges `.sauron/`.

The package publishes `dist/index.js` as the executable binary through `package.json`. Current release metadata is `1.4.7`.

### Init Flow
`runInitCommand` creates a `SessionContext`, selects a presentation driver, runs `ProjectScanner`, optionally prompts the user with inferred defaults, resolves existing manifest configuration, and delegates file orchestration to `InitService`.

`InitService.execute` performs the main installation sequence:
1. Reads or initializes `.sauron/.manifest.json`.
2. Copies base templates from `templates/.sauron` and `templates/.agents`.
3. Generates `AGENTS.md` from selected targets, severity, project context, and stack.
4. Saves manifest configuration and hashes for non-mutable managed files.
5. Builds an `IMemoryPayload` from the canonical template at `templates/.agents/rules/memory.md`, normalizing frontmatter and Sauron markers.
6. Resolves configured AI adapters and calls `inject`.
7. Injects stack-specific wiki recipes through `WikiBootstrapper`.
8. Registers the workspace in `~/.sauron/registry.json`.

### Scanner
`ProjectScanner` is a lightweight scanner. It checks root files and folders, package-manager lockfiles, `tsconfig.json`, known AI tool files/folders for Cursor, Windsurf, Aider, Antigravity, Codex, Opencode, and Claude, `package.json` dependencies, selected compose files, and explicit nested file markers such as `prisma/schema.prisma`. It emits a `ProjectContextInfo` object with language, frameworks, database, styling, package manager, monorepo flag, detected IAs, and wiki recipe names.

### Presentation Layer
`PresentationRouter` chooses between:
- `TerminalDriver`: interactive console with Clack prompts, spinners, and visual diffs.
- `JsonDriver`: structured JSON logs and payloads for automation.

Both drivers implement conflict resolution. Non-interactive flows require `--conflict ours|theirs` when a managed file has diverged.

### Adapter System
`IAgentAdapter` defines `detect`, `inject`, and `clean`. Current adapters support:
- Cursor: `.cursor/rules/sauron-memory.mdc`
- Windsurf: `.windsurf/rules/sauron-memory.md`, with cleanup of legacy `.windsurfrules` blocks.
- Aider: `.sauron-aider-instructions.md` plus `.aider.conf.yml` `read` entries.
- Antigravity: `.agents/rules/memory.md`
- Opencode: `.opencode/instructions/sauron-memory.md` plus `opencode.json` `instructions`.
- Codex: `.codex/rules/sauron-memory.rules`
- Claude: `.claude/rules/sauron-base.md`

### Doctor Flow
`DoctorService` checks:
- Whether the project exists in the central registry.
- Whether `.sauron/.manifest.json` exists.
- Whether manifest-managed files exist and match their stored SHA-256 hashes.
- Whether `.sauron/wiki/summary.json` is valid and referenced wiki files exist with matching hash and byte length.
- Whether expected adapter output files exist and are non-empty for manifest targets, then registry targets, then all supported targets as fallback.

Errors make the report unsuccessful; warnings are reported but do not fail success.

### Uninstall Flow
`UninstallService` removes the project from `~/.sauron/registry.json`, calls `clean` on every registered adapter, removes `AGENTS.md`, and then either:
- Deletes only `.sauron/.manifest.json` while preserving `.sauron/wiki/`, or
- Deletes all `.sauron/` when `--purge` is provided.

### Current Known Risks
- Current installation files are present for Antigravity, Codex, and Opencode, but passive behavior is ultimately mediated by each agent runtime. Sauron injects the instruction surface; it does not enforce a daemon, hook, or runtime policy outside those agent-consumed files.
- `templates/.agents/rules/memory.md` still contains some mojibake characters in symbols such as arrows/check marks, inherited from earlier template encoding.
